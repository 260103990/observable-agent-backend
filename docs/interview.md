# 面试讲解提纲

## 一分钟介绍

这是一个Python/FastAPI Agent后端：以论文RAG形成业务闭环，用PostgreSQL/pgvector保存可追溯的内容和向量，再把内部检索和外部Search注册为受控工具。Trace把模型、工具和Search成本拆开。项目的实验特色是精确Search缓存和同key并发合并，并用冷热/完整Agent对照确认省掉哪些请求，同时保留质量与新鲜度限制。

## 重点问题

1. **数据怎样流转，为什么需要事务？** PDF原始页→规范化文本→同页Chunk/字符范围→文档Embedding；论文、页面、所有向量一次提交，避免元数据存在但索引只有半篇。重复ID不覆盖。
2. **表和SQL如何设计？** paper主键、pages复合主键、chunks复合主键/外键；查询用paper_id参数限定范围，pgvector余弦排序。profile检查与检索使用只读RR快照。没有预先加入ANN索引。
3. **为什么查询前检查模型身份？** 维度相同不代表向量空间相同；保存并核对模型标签、digest、维度和查询表示，避免新旧索引混用。
4. **Loop如何防止失控？** 工具白名单/严格参数、稳定且不重复的call ID、轮数/调用数/超时/历史与结果预算。只读显式瞬时错误才有限重试；副作用工具不能盲重试。
5. **为什么工具结果还要accept阶段？** 先在执行器确认结果可序列化且预算允许，再提交证据账本，防止模型没有实际看到的来源被最终引用。
6. **缓存key、TTL与数据库职责是什么？** key覆盖完整Search请求、提供方/接口、凭据摘要/契约/响应预算；非滑动TTL和LRU处理过期/空间，数据库保存业务事实与Trace。缓存不保存最终生成答案。
7. **并发冷miss如何处理？** 一个请求owner进行HTTP，其余waiter等待通知；取消waiter不取消owner，owner失败通知其他人；有界队列超限旁路。单进程能力，不宣称分布式锁/跨worker共享。
8. **缓存请求少了，为什么不一定快很多？** Agent仍需模型决策和生成；预热有成本。必须分开统计API wall、模型、工具、Search，不重复相加嵌套Span。
9. **有引用为何仍可能说错？** ID合法不等于语义支持，比如来源是每数据集250，回答说每簇250。Prompt不是程序语义validator；固定证据/真实Agent结果需要分层检查。
10. **遇到失败怎么定位？** request_id→Trace→阶段/错误码→模型或工具/数据库/缓存；再用固定输入复现，区分持久化、候选召回、证据预算和生成。HTTP200还可能是limit_reached或部分不足。

讲解时应打开对应源码和测试，而不是只列FastAPI/pgvector等名词。Redis、Worker、多进程共享和生产部署仍是后续方向；已完成的 Docker Compose 是本地演示部署，不能当作已经完成的经历。


## V4 可以结合代码追问的点

1. **写事务存在，为什么读取还会错？** 两个 SELECT 可能跨提交版本；真实暂停在中间让另一个连接覆盖/删除，原实现失败。短只读 RR 保留一致快照，后续请求读取新版本。
2. **为什么批量 Span？** 四 Span 的显式 SQL 6→3；保留序号、重复 ID、JSON 类型和整份回滚。本机对照有数据，不能改写成 Agent 全链路快35%。
3. **如何知道慢在 SQL 还是排队？** 分开量获取/持有/归还与显式SQL/事务往返；获取包括池管理/可能重连，客户端往返也不等于纯服务端执行。
4. **重建容器为什么数据仍在？** PG/PDF 分别在命名卷；真实重建两容器后文件hash、向量与Trace保留并可检索。改变项目名会使用另一套卷，删除卷是另一个操作。
5. **就绪检查和初始化保证什么？** ready 只测本地初始化/业务池/已启用RAG对象，不调用付费模型。初始化用同事务+协作锁，不自动迁移历史 schema；运行故障也不能只靠 depends_on。
